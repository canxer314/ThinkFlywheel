# 工作流示例

> 三个完整的端到端示例, 展示 ThinkFlywheel 在实际场景中怎么用。

---

## 示例 1：典型的一天

> 场景：周二, 你早上打开电脑。vault 里已有 8 个活跃任务和 20+ 原子卡片。

### 08:00 晨报

```
/briefing
```

Claude 生成今日简报 `Daily/2026-06-03.md`：

```markdown
# 2026-06-03 每日简报

## 🔥 今日焦点
1. [[Q2 OKR 复盘报告]] — due in 2 天, 等财务数据
2. [[修复登录超时 Bug]] — 今天开始排查
3. [[健身房恢复训练]] — 今晚

## 📋 活跃任务
| 优先级 | 任务 | 状态 | 下一步 | 更新 |
|--------|------|------|--------|------|
| 🔴 HIGH | [[Q2 OKR 复盘报告]] | waiting | 等财务数据 | 2天前 ⚠️ |
| HIGH | [[修复登录超时 Bug]] | todo | 查看 error log | — |
| MEDIUM | [[面试前端实习生]] | todo | 筛简历 | 昨天 |
| MEDIUM | [[更新 API 文档]] | doing | 写 authentication 部分 | 今天 |
| LOW | [[健身房恢复训练]] | todo | 晚上去 | — |

## 🧠 今日复习（5 张到期）
| 卡片 | 关联任务 |
|------|---------|
| [[SBI 反馈框架]] | → [[面试前端实习生]] 💡 |
| [[REST API 版本管理策略]] | → [[更新 API 文档]] 💡 |
| [[数据可视化三大原则]] | (无关联任务) |

## 📊 项目健康
| 项目 | 状态 | 活跃任务 | 
|------|------|---------|
| [[Q2 OKR]] | ⚠️ at-risk | 3/5, 1 个阻塞 |
| [[API 重构]] | 🟢 on-track | 2/3 |
```

你注意到 `SBI 反馈框架` 恰好在下午面试前到复习期——正好用上。`REST API 版本管理` 关联了今天要写的 API 文档。这就是交叉引用的价值。

### 09:00 开始新任务

```
/task 修复登录超时 Bug
```

Claude 在 `Tasks/active/修复登录超时 Bug.md` 创建笔记, 原始材料堆自动填入了：
- [[登录模块架构]] — 相关概念卡片
- [[上次超时问题的复盘]] — 历史任务
- [[超时排查 Checklist]] — 相关原子卡片

你看到了自己之前总结的排查清单——不用从零开始。

### 11:00 任务阻塞

```
登录超时问题需要运维给权限才能查生产日志, 暂时卡住了
```

Claude 更新任务状态为 `waiting`, 在"问题与吐槽"中追加：
```
[2026-06-03] 需要运维开通生产日志查询权限, 已发工单 #4521。等待中。
```

### 14:00 处理一篇文章

```
/ingest Sources/inbox/远程团队异步沟通最佳实践.md deep
```

Claude 读取文章, 生成阅读摘要到 `Cards/reading/`, 然后自动触发 `/note` 双提议：

```
📋 从本文可提取:

🔗 Wikilinks (已有卡片):
- [[SBI 反馈框架]] — 文中讨论反馈方式时与你的已有知识一致

🆕 建议新建:
| # | 类型 | 标题 |
|---|------|------|
| 1 | atomic | "异步沟通的'5分钟规则'" |
| 2 | insight | "远程团队文档优先 vs 口头沟通的适用边界" |

接受哪些？(all/1/1,2/skip)
> 1,2
```

两张卡片创建完成, 进入 FSRS 复习队列。

### 16:00 完成一个任务

API 文档更新完了。

```
/retro 更新 API 文档
```

Claude 读取任务笔记中的"问题与吐槽"：
```
[2026-06-01] Swagger 生成的文档格式和手动维护的不一致
[2026-06-02] 发现 3 个 endpoint 的示例已经过时
```

AI 分析：
```
📊 模式分析:
- 工具问题: API 文档工具与实际状态不同步
- 流程问题: 缺少 endpoint 变更时同步更新文档的机制

⚠️ 跨任务模式: 这个问题在"修复 XX API 参数"任务中也出现过
```

然后双提议：
```
🆕 建议提取:
| # | 类型 | 标题 |
|---|------|------|
| 1 | insight | "API 文档维护的自动化机会" |
| 2 | atomic | "Swagger 手动维护 vs 代码生成的取舍" |

接受哪些？> all
```

任务归档, 卡片进入 FSRS。

### 20:00 晚间复习

```
/review --limit 5
```

FSRS 引擎返回 5 张到期卡片, 逐一复习。今天有张卡片是第 4 次复习了（"超时排查 Checklist"）, 你评了 Easy, 下次复习被排到了 45 天后。

### 21:00 快速体检

```
/health quick
```

```
总分: 82/100 🟡 良好

⚠️ 警告:
- 1 个僵死任务 ([[整理旧文档]] 17天未更新)
- 3 张孤儿卡片

建议:
- 整理旧文档: 推进或归档
- 孤儿卡片: 检查是否需要链接
```

### 一天总结

今天创建/修改了 10 个文件：1 个任务笔记、1 份晨报、1 份阅读摘要、2 张原子卡片、1 张 insight 卡片、1 份复盘笔记、1 份健康报告。全部通过 wikilink 互联, 全部为明天的晨报积累素材。

## 示例 2：学一项新技能（4 周）

> 场景：你想学 Rust。不是随便看看教程, 而是系统学习并建立长期记忆。

### 第 1 周：搭框架

```
/project 学 Rust   domain: learning
```

Claude 创建 `Projects/active/学 Rust.md`, 你确认了 4 个里程碑：
- [ ] M1: 语法基础 (target: 第 1 周)
- [ ] M2: 所有权和借用 (target: 第 2 周)
- [ ] M3: 异步编程 (target: 第 3 周)
- [ ] M4: 用 Rust 写一个 CLI 工具 (target: 第 4 周)

然后创建具体任务：
```
/task 读完 Rust Book 第 1-3 章   domain: learning
/task 完成 Rustlings 前 20 题    domain: learning
```

`/project` 会自动把 domain 匹配的新任务关联到项目。

### 第 2-3 周：积累知识

你读 Rust Book 的过程中：
- 每读完一章, 跑 `/note` 提取关键概念为原子卡片
- 读到 Rust Blog 的好文章, 丢到 Sources/inbox/, 用 `/ingest` 处理
- 遇到不懂的概念, 用 `/query` 搜 vault："Rust 的 trait 是什么"

3 周后, Cards/atomics/ 积累了 35 张卡片：
- "所有权与借用的区别"
- "Rust 中的 Result 和 Option"
- "生命周期标注规则"
- "async/.await 的本质"
- ...

每晚 `/review`, FSRS-6 根据你的评级自动调度。好记的卡片被推到很远（30-60 天后）, 难记的卡片频繁出现（2-3 天后）。

### 第 4 周：实践和复盘

你完成了 CLI 工具。跑 `/retro 用 Rust 写 CLI 工具`。

Claude 分析"问题与吐槽"：
```
[2026-06-15] borrow checker 一直报错, 花了 2 小时才搞定
[2026-06-16] clap 库的文档例子是旧版本的, API 不对
[2026-06-18] 一开始用 struct 传参, 后来发现用 Builder 模式更好
```

提取 insight：
| # | 类型 | 标题 |
|---|------|------|
| 1 | insight | "Rust 初学者的 borrow checker 调试策略" |
| 2 | insight | "从 struct 到 Builder 模式的重构时机" |
| 3 | atomic | "clap v4 的派生 API vs Builder API 选择" |

### 4 周后

```
/briefing
```

晨报显示：
- 项目 `学 Rust` 🟢 on-track, 2/4 里程碑完成
- 到期复习 4 张 Rust 卡片, 全部关联了活跃任务
- 历史警告："Rust 学习类任务容易在 borrow checker 上卡太久——考虑限制单次调试时间"

你有了 35 张原子卡片、5 张 insight、1 份项目记录、一个稳定运行的复习习惯。以后任何 Rust 任务, `/task` 都会自动从 vault 中找到你的卡片填入"原始材料堆"。

## 示例 3：管理季度项目

> 场景：Q2 OKR, 跨 3 个月, 涉及 10+ 个任务。

### 季度初：立项

```
/project Q2 OKR   domain: work
```

章程：
```markdown
## Goal Statement
Q2 结束时, 完成 API 重构 + 新版 Dashboard 上线 + 团队招聘到位。

## Key Milestones
- [ ] M1: API 重构设计评审通过 (4 月底)
- [ ] M2: Dashboard MVP 内测 (5 月中)
- [ ] M3: 招聘 2 人入职 (6 月中)
- [ ] M4: 全量上线 (6 月底)
```

然后创建了 10+ 个 `/task`, 每个关联到对应里程碑。

### 月度中期：检查

```
/project status Q2 OKR
```

```
Progress Pulse: ⚠️ at-risk
Last updated: 2026-05-20

活跃任务: 7/10
- 5 doing, 1 waiting (阻塞), 1 todo

M1 完成 ✅
M2 进行中, 当前进度 60%
M3 未开始, 应在 5 月底启动

Risk Log（从任务"问题与吐槽"汇总）:
- "Dashboard 依赖的后端接口改了 2 次" → 范围不稳定
- "候选人 OKR 面试排不上" → 招聘流程瓶颈
```

你及时发现招聘可能会延误, 提前调整了优先级。

### 季度末：复盘

```
/retro Q2 OKR --type project
```

跨任务模式被检测出来：
```
⚠️ 重复模式检测:
3 个任务出现了'等待其他团队确认'的阻塞问题。
Q1 OKR 的复盘中也出现了相同模式。

→ 这是一个组织级模式, 不只是项目级的问题。
```

提取的 insight：
- "跨团队依赖是 Q2 最大的进度风险——3/10 的任务被外部团队阻塞"
- "API 重构类任务容易范围蔓延——2 个任务实际工作量是预估的 2 倍"

项目归档, 所有教训进入 FSRS。下次 Q3 OKR 立项时, `/project` 会自动搜索到 Q2 的复盘和这些 insight 卡片, 填入初始风险评估——**你不会重复同样的错误**。

## 三种场景对比

| | 典型的一天 | 学新技能 | 季度项目 |
|---|---|---|---|
| 核心技能 | /briefing /task /retro /review | /project /task /note /ingest /review /retro | /project /task /retro /health /decide |

| 卡片产出 | 3-5 张 | 30+ 张 | 10+ insight |
