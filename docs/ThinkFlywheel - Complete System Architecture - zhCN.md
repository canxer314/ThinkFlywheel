ThinkFlywheel (知行飞轮)：完整系统架构

1. 系统名称与核心理念

名称：ThinkFlywheel (知行飞轮)

核心理念：每一次任务完成，都应让未来的每一次任务更简单。没有行动的知识是死的；没有知识的行动是盲的；两者没有记忆则是白费的。这不是一个知识管理系统或任务管理器——它是你认知的个人复利引擎。

三条设计公理：
1. 行动喂养知识，知识喂养行动——双向流动是系统的心跳
2. 记忆是桥梁——间隔重复确保知识在创造它的任务结束后依然存活
3. AI 做广度，人做深度——AI 扫描、提议、格式化；人判断、决定、创造

适合谁：
- 跨多个领域的个人知识工作者（开发者、研究员、PM、创业者）
- 尝试过 Obsidian/Tana/Notion 做 PKM，但发现"知道≠做到"的人
- 愿意投入 8-12 周渐进式采用，而非一次性部署的人
- 熟悉终端、Git 和基础 Python 的人

2. 分层架构

+===================================================================+
|  L4: 治理层                                                        |
|  /health（跨系统检查）+ /decide（决策记录）                          |
|  AI 扫描：断链、孤儿卡片、进度-健康差距、知识-行动断层、矛盾检测      |
+===================================================================+
        |                        |                        |
        v                        v                        v
+-------------------+  +-------------------+  +-------------------+
| L3: 任务层        |  | L2: 知识层        |  | L1: 记忆层        |
| (防弹笔记法)       |  | (LLM Wiki)        |  | (FSRS-6 间隔重复) |
|                   |  |                   |  |                   |
| 防弹笔记           |  | 原子卡片          |  | 间隔重复          |
| /task /project    |  | /note /ingest     |  | /review           |
| /retro /flow      |  | /query            |  | fsrs_engine.py    |
|                   |  |                   |  |                   |
| "要做什么"         |  | "我知道什么"       |  | "我记住什么"       |
+-------------------+  +-------------------+  +-------------------+
        ^                        ^                        ^
        |                        |                        |
        +------------------------+------------------------+
                所有数据通过 Obsidian Vault 流转
                以纯 Markdown 文件形式，Git 版本控制

关键洞察：这不是一个上层比下层更重要的堆栈。这是一个飞轮，每一层都在强化其他层。任务完成产生知识（/retro → /note）；知识进入记忆层（/review）；记忆中的知识在新任务中浮现（/briefing）；执行得更好的任务产生更好的知识。这就是复利引擎。

四个领域的整合方式：

┌────────────────┬────────────────┬──────────────────────────────────────────────────────────┐
│     领域       │   主要层级     │                       整合点                               │
├────────────────┼────────────────┼──────────────────────────────────────────────────────────┤
│ 防弹笔记法     │ L3 (任务)      │ 四要素模板作为通用任务容器；"问题与吐槽"喂养 L2 知识提取   │
├────────────────┼────────────────┼──────────────────────────────────────────────────────────┤
│ LLM Wiki       │ L2 (知识)      │ 编译模式：AI 维护 Cards/、index.md、log.md；/ingest 处理源  │
├────────────────┼────────────────┼──────────────────────────────────────────────────────────┤
│ FSRS/原子笔记  │ L1 (记忆)      │ fsrs_engine.py；/review 使用 FSRS-6；任务洞察产生 SR 卡片  │
├────────────────┼────────────────┼──────────────────────────────────────────────────────────┤
│ Agent-PMO(简化)│ L3+L4          │ /project 替代 /initiate+/plan+/monitor；/health 适配检查   │
└────────────────┴────────────────┴──────────────────────────────────────────────────────────┘

4.5 详细技能规格

/task —— 防弹任务笔记管理器

触发词："new task"、"create task"、"start task"、"任务"、"新建任务"

输入：任务描述（必填），领域（默认：work）

行为：
1. AI 在 Tasks/active/{任务名}.md 中创建带预填四要素模板的任务：
    - 🎯 最终目标：AI 根据任务描述起草——用户完善
    - 📎 原始材料堆：AI 内部运行 /query 查找 vault 相关内容，填充初始参考资料
    - ⚡ 下一步行动：AI 提议 2-3 个具体的第一步动作
    - 💬 问题与吐槽：留空，用于在执行中记录摩擦
2. AI 更新 index.md 和相关 MOC
3. 返回创建的笔记内容

关键设计选择：这与 knowledge-mgmt 的方法相反。在 knowledge-mgmt 中，/note 是唯一的写入通道。在这里，/task 也可以直接写入，因为任务不是知识——它们是行动容器。双提议过滤在任务完成的 /retro 阶段执行，而非任务创建时。

准入校验（Step 0）：创建前，AI 用 Esor 的四个过滤器验证：
1. 行动承诺：用户是否真的打算为此投入时间？
2. 具体成果：完成时能交付什么可验证的产出？
3. 多步骤性：是否需要 2 步以上？（单步动作 → 建议直接做掉）
4. 需整合信息：是否需要从多个来源汇集信息？

如果想法未通过这些过滤器但仍值得保留 → 写入 Inbox/，供后续 triage。

/briefing —— 每日晨间上下文

触发词："briefing"、"morning"、"today"、"晨报"、"今天"、"早上好"

输入：无

行为：
1. 扫描 Tasks/active/ 中所有进行中的任务
2. 调用 fsrs_engine.py stats 获取到期复习卡片
3. 交叉引用：哪些到期卡片关联了哪些活跃任务（通过 related_cards frontmatter）
4. 检查 Projects/active/ 中的目标级健康警告
5. 生成结构化简报 Markdown，包含以下板块：
   - 🔥 今日焦点（1-3 件最重要的事）
   - 📋 活跃任务（按优先级排列）
   - 🧠 到期复习卡片（交叉引用活跃任务）
   - 📊 项目健康
   - ⚠️ 历史预警（类似历史任务的踩坑记录）
   - 📥 Inbox 计数（未处理的闪念）
6. 将简报写入 Daily/YYYY-MM-DD.md

为什么重要：这是关键的"融合点"，三层在此汇聚为一张可操作的早晨视图。它解决了所有 10 份报告指出的问题：复习与任务脱节，任务与知识脱节。

/note —— 知识提取（双提议）

触发词："note"、"做笔记"、"存笔记"、"原子笔记"

输入：范围（全部对话 / 上次讨论 / 手动选择）

行为：主要复用 knowledge-mgmt 的 /note，做了修改：
1. 扫描对话中值得保留的知识内容
2. 展示 研究摘要——一张叙事性卡片
3. 展示 双提议：
    - 提议 1：链接到已有卡片的 Wikilinks（AI 建议，用户逐条确认）
    - 提议 2：建议新建的原子卡片（AI 建议，用户选择接受哪些）
4. 将确认的写入执行到 Cards/
5. 更新 MOC 索引
6. 如果有任务上下文，为创建的卡片添加 related_tasks: [[任务名]]

相较 knowledge-mgmt 的关键修改：增加了自动 related_tasks 标签。当 /note 在任务会话中被调用时，创建的卡片自动回链到任务。这就是 knowledge-mgmt 缺失的"任务锚点"。

/review —— 间隔重复

触发词："review"、"复习"、"今天复习什么"

行为：直接复用 knowledge-mgmt 的 /review：
1. 扫描新的 type/atomic 卡片
2. 通过 fsrs_engine.py bulk_register 将它们注册到 review_state.json
3. 查询 fsrs_engine.py due 获取到期卡片（混合新卡/复习卡，默认 50/50）
4. 逐一展示卡片，用户自评（1=Again 完全忘了, 2=Hard 记得一点, 3=Good 基本记得, 4=Easy 太简单）
5. 通过 fsrs_engine.py record 将评分提交给引擎进行调度

状态：这是最成熟的组件。fsrs_engine.py 经过实战检验。几乎不需要适配。

/retro —— 任务/项目复盘与三向回流

触发词："retro"、"done"、"完成"、"复盘"、"close"

输入：任务或项目名称

行为：这是关键的桥接技能——任务执行在此喂养知识。
1. 读取任务/项目笔记，尤其是"问题与吐槽"
2. AI 分析：重复模式、经验教训、意外结果
3. 跨任务模式检测：搜索同领域历史任务中的重复摩擦
4. 三向知识分发（三向回流）：
    - 路径 1：通用方法论 → Cards/atomics/ + Cards/insights/（通过 /note 双提议创建原子卡片）
    - 路径 2：流程级经验 → 回写 Flows/{domain}/（更新步骤/易错点，递增版本号）
    - 路径 3：专案级洞察 → 回写 Projects/active/（更新经验区）
5. 将任务移至 Tasks/archived/，更新状态
6. 将复盘摘要写入 Reviews/retro/

为什么存在：这填补了 knowledge-mgmt 和 agent-pmo 共有的缺口。knowledge-mgmt 有 NOTE 但没有 TASK 完成触发器。agent-pmo 有 /close 但没有知识提取。这个技能将它们桥接起来。三向回流解决了几乎所有任务系统的核心缺陷：经验被困在单个任务内部，无法跨任务复用。

/query —— Vault 搜索

触发词："query"、"find"、"search"、"查询"、"搜索"

行为：与 knowledge-mgmt 的 /query 类似：
1. 先读 index.md 进行大范围导航
2. 搜索 vault 中相关卡片、任务、决策、项目
3. 综合回答，带 [[wikilinks]] 引用
4. 好的回答可保存为新卡片（触发 /note 流程）

搜索策略（按优先级）：
1. 精确标题匹配 → 2. 标签过滤（domain + 关键词）→ 3. 全文内容搜索 → 4. 链接扩展（沿 wikilink 追 2 跳）

/ingest —— 来源处理

触发词："ingest"、"process"、"read this"、"处理"、"阅读"

输入：来源文件路径或 URL

行为：从 knowledge-mgmt 的 /read + /insights 简化而来：
1. 读取来源材料
2. 生成结构化摘要
3. 标记与已有 vault 知识的矛盾
4. 触发 /note 流程进行知识提取
5. 将来源移至 Sources/processed/
6. 更新 index.md 和 log.md

处理深度：
- quick（默认）：核心论点 + 关键论据 +"与我何干"
- deep：quick + vault 交叉引用 + 矛盾检测 + 活跃任务关联

/project —— 个人目标管理器（从 agent-pmo 简化）

触发词："project"、"goal"、"目标"、"项目"

输入：目标描述，领域

行为：用 1 个技能替代 agent-pmo 的 15 个技能：
1. 创建 Projects/active/{项目名}.md，包含：目标陈述、动机、关键里程碑、关联任务、风险日志、进度脉搏
2. AI 查询 vault 中相关历史项目/洞察
3. 每周：AI 扫描关联任务，更新进度脉搏（🟢 on-track / ⚠️ at-risk / 🔴 stalled）
4. 任务通过领域匹配或手动 project 字段自动关联

/flow —— 永久型 SOP/流程笔记

触发词："flow"、"流程"、"SOP"、"建立流程"

输入：流程名称，领域，触发条件（可选）

行为：
1. 创建 Flows/{domain}/{名称}.md——永久模板，永不归档
2. 如果存在历史相似任务，提取共性步骤/易错点作为初始内容
3. 触发条件（weekly-fri、monthly-1、on-demand）通过 /briefing 激活

/health —— 跨系统健康检查

触发词："health"、"check"、"体检"、"lint"

行为：在 knowledge-mgmt 的 /lint 基础上扩展跨系统检查：
quick 模式（6 项检查）：断链、任务僵死（14+ 天）、复习积压、项目异常、孤儿卡片、空 MOC 区间
full 模式（额外 4 项）：知识-行动断层、领域平衡（7 个领域）、矛盾检测、溯源完整性

评分维度（满分 100）：
链接健康(20) + 任务活力(20) + 知识-行动一致(20) + 记忆保持(15) + 领域平衡(10) + 溯源完整(10) + 结构完整(5)

/decide —— 决策记录器

触发词："decide"、"decision"、"决策"

输入：决策描述

行为：
1. 创建 Decisions/DEC-{YYYY}-{NNN}.md
2. AI 预填上下文：查询 vault 中相关知识和历史类似决策
3. 模板包含：上下文与约束、所有选项（利弊/风险/最坏情况）、选择 + 理由 + 关键假设、预期结果
4. 决策复查提醒进入 FSRS 队列（30 天后）
5. 复查时：对比实际结果与预期；决策被推翻 → 创建 insight 卡片

/meeting —— 会议处理

触发词："meeting"、"会议"、"会议纪要"、"转录"

行为：
1. 处理会议转录/笔记
2. 创建结构化会议纪要到 Cards/reading/，subtype: meeting
3. 提取：决策、行动项（→ /task）、风险、跟进事项

融合点 3：任务完成（/retro）

融合点 4：来源处理（/ingest）

knowledge-mgmt：  /read → /note 流水线适配

结果：            阅读喂养行动，而不仅仅是好奇心

融合点 5：决策制定（/decide）

融合点 6：健康检查（/health）

knowledge-mgmt：  链接健康、标签合规、来自 /lint 的剪辑库存

Agent-PMO 提供：  进度-计划偏差
防弹笔记法：      任务僵死检测

6. 关键设计决策（10 份报告意见分歧之处）

决策 1：系统范围——12 个技能，而非 15 个

所有 10 份报告都同意：agent-pmo 的 15 个技能对个人使用来说太多了。分歧在于保留 4 个、6 个还是 8 个。

决策：总共 12 个技能，4 个组 + 工具组。理由：
- 4 个会完全失去项目层（多份报告主张保留部分 PMO）
- 8 个更接近企业级但仍过多
- 12 个给我们：执行(4) + 知识(3) + 记忆(2) + 治理(2) + 工具(1)——每组可独立可选采用

决策 2：起点——防弹笔记法先行

分歧：基础设施先行（DeepSeek）vs. 防弹笔记先行（Claude、Kimi、ChatGPT）

决策：防弹笔记先行（Phase 1 只用 /task 两周）。理由：
- 用户已有 LLM 分析经验但缺乏系统实践
- 防弹笔记产生即时价值（你把事情做完了）
- 知识系统需要内容才能发挥作用——任务产生这些内容
- 这遵循 Esor 自己的哲学："不要先设计完美的系统。先开始做。"

决策 3：AI 自主权——降低摩擦的双提议

分歧：全自动（Karpathy）vs 强制确认（knowledge-mgmt）vs 中间路线

决策：分级自主权。按风险分为三级：
- AI 自主：MOC 更新、index 更新、log 追加、剪藏移动、健康报告生成、每日简报生成、项目进度脉搏更新、inbox 捕获
- AI 提议 + 人确认：原子卡片创建、已有卡片的 wikilink 添加、复盘卡片提取（保留双提议）
- 仅人操作：任务优先级排序、项目目标设定、决策制定、schema 变更

这比 knowledge-mgmt 更自主（增加了 MOC、index、log、简报的自主操作），但比 Karpathy 的愿景更保守（人仍然把关所有知识写入）。

决策 4：间隔重复缺口——必须包含

分歧：部分报告希望集成 SR，其他报告认为 wiki 查询可以替代它。

决策：FSRS-6 是不可协商的。理由：
- Karpathy 的 wiki 和 agent-pmo 都没有 SR——这是一个真实的缺口
- knowledge-mgmt 的作者明确论证："一个编译精美但从未被记住的 wiki 是浪费"
- SR 使系统成为"个人资产"而非"AI 资产"——它把知识推入你的大脑
- ChatGPT 的报告将此识别为核心"知识→长期记忆"缺失环节

决策 5：目录结构——英文加中文命名空间

分歧：agent-pmo 使用中文目录；knowledge-mgmt 使用英文。

决策：英文目录名 + 通过 Obsidian 别名显示中文名。理由：
- 英文名称更适合 CLI 工具和脚本
- 中文名称更适合人工浏览（Obsidian 别名桥接两者）
- 这与 knowledge-mgmt 的方法相同（除了它的"已研究"目录例外）

决策 6：/task 作为额外写入通道

分歧：knowledge-mgmt 强制 /note 为唯一写入通道。部分报告建议 /task 也应写入。

决策：/task 直接写入任务笔记；知识卡片仍通过 /note 双提议。理由：
- 任务是行动容器，不是知识——不需要同样的质量门控
- 要求任务创建走双提议会增加摩擦，违背防弹笔记的初衷（速度与动量）
- 质量门控应用于 /retro 时——任务完成、洞察提取之际

决策 7：闪念捕捉——无自动化的 Inbox

分歧：GTD 式通用收件箱 vs. 直接到任务 vs. 完全不要收件箱。

决策：添加 Inbox/ 目录作为轻量捕捉区，无专属技能。理由：
- 有些想法对 /task 来说太模糊（无法通过四过滤器校验），对 /note 来说太原始（未经验证、未处理）
- 直接写入 Inbox/ 保持捕捉摩擦接近零——用户只需说出念头
- Triage 由用户手动、按自己的节奏进行：转为 /task、/note 或丢弃
- 无自动化、无新命令——只有一个目录、一个模板和一个约定

Phase 3：记忆层（第 5-6 周）

构建技能：/review（集成 fsrs_engine.py）

Phase 5：治理 + 调优（第 9-12 周）

构建技能：/health

做什么：开始每周健康检查。根据实际使用完善 SCHEMA.md。个性化模板。调优 FSRS 参数。

成功指标：每周健康检查至少识别出一项可操作的改进。

9. 技术栈深探

9.1 Obsidian——为什么是强制依赖

Obsidian 提供的是基础平台，而不仅仅是编辑器：

CLI（≥ 1.12）：100+ 命令通过 IPC 进行 vault 文件操作
├── create/read/append/delete/move（自动同步 wikilinks）
├── property:set/read/remove（YAML frontmatter 操作）
├── search/search:context（全文搜索）
├── backlinks/links/unresolved/orphans（链接图谱查询）
└── tasks/tags（结构化查询）

Obsidian Flavored Markdown（OFM）：
├── [[wikilink]]   → 双向链接是核心的组织原语
├── ![[embed]]     → 内嵌其他卡片内容
├── > [!callout]   → 结构化提示块
└── ---frontmatter → YAML 元数据驱动所有查询和索引

关键约束：所有 vault 文件操作（创建/读取/修改/移动/删除）必须通过 obsidian CLI 执行。禁止用 Write/Edit/Bash 直接操作 .md 文件。这确保了 Obsidian 内部 API 的 wikilink 同步和 frontmatter 校验。

插件生态：
├── Dataview    → 在 MOC 和健康报告中利用 frontmatter 生成动态表格
└── Web Clipper → 网页捕获到 Sources/inbox/

9.2 FSRS-6 间隔重复引擎

vault/.obsidian/scripts/fsrs_engine.py（629 行，纯 Python stdlib——零外部依赖）：

命令：
├── due           → 获取到期卡片（混合新卡/复习卡，默认 50/50 比例）
├── record        → 记录评分（Again/Hard/Good/Easy）并更新状态
├── register      → 注册单张新卡片
├── bulk_register → 从 stdin JSON 批量注册（/review 扫描 vault 时使用）
├── record_session→ 记录复习会话摘要
├── retire        → 退役卡片（从复习池中移除，保留在状态文件中）
└── stats         → 打印统计信息（by_state、due_today、rating_distribution 等）

核心算法：
├── 21 个默认参数（w[0]..w[20]）— FSRS-6 官方默认值
├── Power-law 遗忘曲线：R(t,S) = (1 + factor × t/S)^(-w20)
│   factor = 0.9^(-1/w20) - 1
├── 难度更新（带线性阻尼的均值回归）：
│   D' = D + delta_D × (10-D)/9, 然后 D'' = w[7]×D₀(4) + (1-w[7])×D'
├── 成功后的稳定性（rating=2 时有 hard_penalty，rating=4 时有 easy_bonus）：
│   S' = S × (e^w[8] × (11-D)^w[9] × S^(-w[10]) × (e^(w[11]×(1-R))-1) × penalty × bonus + 1)
├── 遗忘后的稳定性（lapse 后，永不超过之前的稳定性）：
│   S' = w[11] × D^(-w[12]) × ((S+1)^w[13]-1) × e^(w[14]×(1-R))
├── next_interval：反解遗忘曲线，找到 R(t,S) = target_retention 时的 t
└── 原子写入：tempfile.mkstemp + os.replace（无部分写入）

状态文件：.obsidian/review_state.json（JSON 格式）
├── cards: { id: { title, content_snippet, state, difficulty, stability, due_date, reps, lapses, review_log[] } }
├── params: { w[], target_retention, max_interval_days }
├── scan_history: { last_scan, known_card_ids[] }
└── session_history[]

9.3 Claude Code 作为 AI 运行时

所有 ThinkFlywheel 的 AI 行为通过 Claude Code 斜杠命令运行。每个技能 = 一个 SKILL.md 文件：
- 调用方式（触发词）
- 参数 schema（YAML frontmatter）
- 行为规格（分步流水线）
- 失败处理表（场景 → 恢复操作）
- 反模式黑名单（# → 反模式 → 为什么 → 正确做法）

vault/.claude/rules/ 中的 9 个规则文件在会话启动时自动加载为 ground truth。AI 不需要手动读取它们——它们始终在上下文中。

9.4 技术选型总览

| 组件         | 技术                         | 理由                                               |
|--------------|------------------------------|----------------------------------------------------|

10. 工程设计模式与规范

10.1 核心原则

1. "AI 做广度，人做深度"——AI 扫描、提议、格式化、索引；人判断、决定、创造。三级自主权模型的理论根基。

2. 文件即数据库——没有 SQL/NoSQL。所有数据存储在 Markdown 文件中，通过 wikilinks 组织，通过 YAML frontmatter 结构化。Git 提供版本历史。

3. "不删，只归档"——铁律 2 确保信息永不丢失。这降低了 AI 错误的破坏半径——最坏情况是创建多余的卡片，而非摧毁数据。

4. 双提议机制——所有知识卡片"先展示、后确认再写入"。AI 做广度的扫描和提议工作；人做深度的选择工作。

5. 任务不是知识——/task 直接写入（无需双提议），因为任务是行动容器，不是认知资产。质量门控延迟到 /retro 时执行。

6. 渐进式采用——5 个 Phase，8-12 周。从 /task + /briefing 开始，每个 phase 增加一个新技能。不是"安装即用所有功能"。

10.2 溯源链

Sources/inbox → /ingest → Cards/reading/ (type/reading)
                                ↓ /note 提取
                         Cards/atomics/ (type/atomic)

Tasks/active/ → /retro → Cards/insights/ (type/insight)
                              ↓ /note 提取
                         Cards/atomics/ (type/atomic)

- reading.source → 回链 Sources 文件
- atomic.source → 回链其来源 reading、insight 或 task
- 配合 agentmemory 的 commit-context，连 git 历史都能追溯到产生每次变更的会话和任务

10.3 索引一致性

每次写入操作同步更新：
- index.md——内容导向目录
- log.md——按时间追加的只增记录
- 相关 MOC——领域级聚合

这防止了多次 AI 操作和会话之间的状态漂移。

11. 集成层：三系统记忆架构

11.1 记忆分工

┌──────────────────────────────────────┐
│ ThinkFlywheel — 人的外脑             │
│ "我知道什么、在做什么、记住了什么"     │
│ 存储：Obsidian vault (MD + Git)      │
├──────────────────────────────────────┤
│ planning-with-files — Agent 工作内存  │
│ "我在哪一步、下一步是什么"            │
│ 存储：.planning/ 目录                │
├──────────────────────────────────────┤
│ agentmemory — Agent 长期记忆         │
│ "上次我们聊了什么"                    │
│ 存储：MCP 插件持久化                  │
└──────────────────────────────────────┘

11.2 四个协同点

1. 任务执行闭环：
   /task 定义"要做什么"→ planning-with-files task_plan.md 拆成 phase
   → 完成后 /retro 将经验提取回 ThinkFlywheel

2. 双重会话恢复（/clear 或重启后）：
   agentmemory handoff 恢复对话语义（"我们在聊什么"）
   + planning-with-files session-catchup 恢复执行状态（"做到哪一步了"）

3. 双向知识沉淀：
   人的经验 → ThinkFlywheel FSRS（推入人脑）
   Agent 的经验 → agentmemory memory_save（未来类似任务召回）

4. 代码溯源：
   agentmemory commit-context 追溯每次文件变更到具体会话和 ThinkFlywheel 任务

11.3 何时启用各层

| 场景                    | 仅 ThinkFlywheel  | + planning-with-files  | + agentmemory       |
|-------------------------|-------------------|------------------------|---------------------|
| 小事（回复邮件）         | /task 够用         | 不需要                 | 不需要              |
| 中等（周报）             | /task + /retro     | 可选（步骤 > 5 时）     | 不需要              |
| 复杂（Q2 复盘）          | /task + /retro     | 推荐（跨多天）          | 推荐                |
| 跨会话项目              | /project           | 强烈推荐               | 强烈推荐             |
| 多人协作项目            | /project + /decide | 必需                   | 必需                |

经验法则：任务超过 5 个步骤或跨天执行 → 启用 planning-with-files。跨 3 个以上会话 → 启用 agentmemory。

12. 优势、风险与当前局限

12.1 核心优势

- 真正的双向流动：大多数系统只有"知识→查询"的单向通道。ThinkFlywheel 的行动→知识→记忆→新行动飞轮是闭环的。
- 设计成熟度高：每个技能有完整的失败处理表 + 反模式黑名单 + 准入校验。
- 不可逆操作保护：铁律（不删除、双提议、SCHEMA 审批）构成多层安全网。
- 普适但不空泛：覆盖 7 个生活领域，每层有具体可执行的技能。
- 纯文件架构：不依赖任何云服务或专有数据库。数据完全在用户控制下。
- 技能工程规范统一：每个 SKILL.md 遵循相同的模板（准入检查 → 流水线 → 失败处理 → 反模式）。

12.2 风险

| 风险                    | 严重度 | 缓解措施                                                          |
|-------------------------|--------|-------------------------------------------------------------------|
| Obsidian 强依赖         | 高     | Obsidian 是成熟产品，CLI 自 1.12 起稳定；但方向变化 = 大量重构     |
| Claude Code 依赖        | 中     | 技能是 Claude Code 斜杠命令；迁移到其他 Agent 需重写 skill 层      |
| 学习曲线                | 中-高  | 12 个技能 + 11 种卡片 + 9 条规则；渐进式采用路线图缓解             |
| 初期"空"问题            | 低     | vault 为空时 /briefing 和 /query 价值有限；ROI 随使用时间增长      |
| Windows CLI 边界情况    | 低     | obsidian-cli.md 处理了 Obsidian.com vs Obsidian.exe、8KB chunk boundary bug、CJK 编码 |
| 无多人支持              | 低     | 设计为单人使用；Git 提供版本历史但无合并冲突解决机制                |

12.3 当前局限

- 无自动化测试：零单元/集成/E2E 测试。技能正确性完全依赖 LLM 遵循 SKILL.md 规格。
- 无 CI/CD：技能优化依赖手动 /darwin-skill 评估；没有 pre-commit hook 或自动化检查。
- FSRS 参数固定：使用 FSRS-6 默认参数；无自动调优（尽管可以手动编辑 review_state.json）。
- 无移动端：完全依赖 Obsidian 桌面端 + Claude Code CLI。移动端只能通过 Obsidian Mobile 查看，无法触发 AI 操作。
- 技能以 Markdown 规格存在而非可执行代码：行为一致性依赖 LLM 的理解能力。

核心改进：

knowledge-mgmt 是一个知识编译器——它将来源处理成卡片，但与行动没有连接。

agent-pmo 是一个项目编译器——它追踪项目各个阶段，但没有记忆或个人生活维度。

ThinkFlywheel 是一个生活编译器——它将你的行动、知识、决策和项目编译进一个单一协调的系统，其中一切都在强化其他一切。两个前身共有的根本缺口（知识与行动脱节）在架构层面通过 /task 和 /note 经 /retro 的双向流动得以解决。

使之成为可能的三个核心融合点：
1. 晨间融合（/briefing）——将任务、知识和记忆层拉入一张可操作的视图
2. 完成融合（/retro）——通过三向回流将行动摩擦转化为可复用知识
3. 创建融合（/task）——在创建新任务时自动浮现旧知识
