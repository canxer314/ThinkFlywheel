# /meeting Command

会议转录处理专用技能 — 飞轮的高频燃料注入口。

## 核心理念

> 会议的核心产出是承诺、决议、摩擦——知识提取是副产品。设计哲学和模式对比见 [DETAIL.md](DETAIL.md)。

## Behavior

### Step 0: 准入与定位（创建任何东西之前）

读取转录文字后，先回答用户三个问题以建立处理上下文：

**0.1 会议身份** — AI 推断 + 用户确认：

- **时间**：从文件名或转录内容中提取日期
- **参会人**：从转录中的说话人标记提取，如无，询问
- **类型**：客户会 | 内部协作 | 1-on-1 | 评审 | 培训 | 其他
- **关联专案**：AI 扫描 `Projects/active/`，根据关键词推断候选专案 + 用户确认

**0.2 会议视角** — 用户在会议中的角色：

- 主持/决策者 / 参与者 / 旁听 / 客户方
- 决定行动项的归属判断——只有"我承诺的"才会变成 Task

**0.3 历史链接** — AI 搜索同参会人或同专案的历史上下文（双通道）：

**Vault 通道**（按优先级）：
1. `Cards/reading/` 中 `subtype: meeting` + 相同 `project` 的最近纪要
2. 相同 `participants` 中重叠 ≥ 2 人的最近纪要
3. 文件名或标题中包含相同关键词（客户名、项目名）的纪要

**【MCP 通道】跨会话历史召回**：
- `memory_smart_search` 用参会人 + 项目名搜索 → 找历史上与这些人的所有讨论（包括未写成会议纪要的临时沟通、快速同步）
- `memory_recall` 用项目名 + 关键议题召回 → 找到以前的讨论背景和未记录的决策上下文
- MCP 结果与 vault 记录不冲突 → 融合进历史链接；冲突 → vault 胜出

找到候选后展示给用户，用户确认关联哪些（标注来源：vault / MCP / 两者）。若用户确认了 `prev_meeting`，写入纪要 frontmatter。

### Step 1: 说话人与段落结构化

转录文字**保证有说话人标记**（如"张总:"、"客户:"、"我:"）。按此标记：

1. **按议题分块**（不是按时间顺序——会议常在一个议题上来回跳）
2. **标记每个段落的 utterance 类型**：
   - 🎯 **决议性陈述**："我们决定..."、"那就这么定"、"最终方案是"
   - 📋 **承诺性陈述**："我来负责..."、"下周给你"、"这个交给我"、"我回去做"
   - ❓ **待解决问题**："这个还不清楚"、"需要再确认"、"还要看"
   - 💭 **信息/观点陈述**：背景说明、方案介绍、数据展示
   - 🚧 **摩擦/反对/顾虑**："我有顾虑"、"不太行"、"风险在于"、"问题是"

**关键区分**：
- "我（用户）承诺给别人的" → 候选 Task
- "别人承诺给我的" → 不建 Task，记入"行动项（对方）"追踪
- "别人承诺给别人的" → 不追踪

### Step 2: 四维提取（并行）

四类输出并行提取，各有独立的处理路径。

#### 2A. 决议提取 → 走 `/decide` 通道

识别明确的"我们决定 X"或"最终方案是 X"。对每个决议准备：

- 决议内容（一句话）
- 备选方案（如果会议中讨论了）
- 决议理由（转录中提到的 why）
- 关联专案

输出格式：候选 Decision 列表，待 Step 5 统一确认。

**过滤**：不是所有"我觉得"都是决议。决议必须是多方达成共识或决策者拍板的结论。

#### 2B. 行动项提取 → 走 `/task` 通道

识别**所有说话人的承诺性陈述**，然后按归属分流：

**我方行动项**（候选 Task）：

对每个我方承诺，尝试填充 A-F-O-T：

| 要素 | 来源 |
|------|------|
| **动词** | 从转录提取："撰写/发送/约见/调研/修改/对齐" |
| **对谁** | 受益方："给A客户/给张工/给团队" |
| **成果** | 可验证产出："技术文档/接口字段表/邮件确认" |
| **时地** | 转录中提到的截止日；若无，标记 ⚠️ 要求用户补 |

对每个候选 Task，走 `/task` Step 0 的四过滤器自检：
1. 行动承诺？（不是兴趣/愿望）
2. 具体成果？（可验证产出）
3. 多步骤性？（≥ 2 步）
4. 需整合信息？

- 通过 → 候选新建 Task
- 单步动作（2 分钟内可完成）→ 建议直接做掉，不建任务
- 模糊意向 → 反问用户具体成果

**他人行动项**（不建 Task，追踪用）：

- 记录：`{人}: {承诺事项} — 期望 {截止日}`
- 写入会议纪要的"行动项（对方/他人）"节
- 下一次同参会人会议时，`/meeting` 的 Step 3 自动对照

**对已有任务的更新**：

如果行动项明显是已有 Task 的进展（关键词匹配任务标题或完成定义）：
- 准备追加进度日志到该 Task
- 勾选对应行动步骤（如果完成）
- 更新 Next Action（如果当前步骤已完成）

#### 2C. 知识提取 → 走 `/note` 双提议

只提取**有反复使用价值**的内容，会议中的临时讨论不进卡片。

**值得沉淀**：
- 客户的具体需求/痛点 → insight 候选
- 行业/产品的新认知 → concept 候选
- 反复出现的模式/原则 → atomic 候选
- 纠正的误解 → insight 候选

**跳过**：
- 会议流程性内容（"那我们开始吧"）
- 纯状态更新（"这个东西还在做"）
- 没有复用价值的临时讨论

输出：`/note` 风格的双提议（wikilink 链接已有卡片 + 新卡片创建提议）。

#### 2D. 风险/悬而未决追踪 → 回写到 Project

识别以下内容，准备追加到关联 Project：

- **暴露的风险**："交付时间紧"、"关键人休假"、"第三方依赖不稳定"
- **未达成共识的争议点**：团队内部意见分歧
- **客户的隐性顾虑**："对方虽然没有明说，但似乎在担心 X"
- **需要升级的问题**：单任务无法解决，需专案级决策

输出：候选追加到 Project 笔记的对应区域。

### Step 3: 历史模式对照

仅在以下条件之一满足时执行：
- `mode = deep`
- Step 0 中用户确认了 `prev_meeting` 关联

对照内容：

**3.1 承诺履约对照**：

对比上次纪要的"行动项（我方）"与本次会议内容：
- 已完成且本次提及 → 在原 Task 追加完成记录
- 未完成且本次提及进展 → 在原 Task 追加进度日志
- 未完成且本次**未提** → ⚠️ 标记"上次承诺未跟进"，提示用户

**3.2 对方行动项追踪**：

检查上次纪要的"行动项（对方/他人）"：
- 本次会议中对方是否兑现？
- 未兑现且本次未提 → 提示用户是否需要在下次沟通中追问

**3.3 重复问题预警**：

上次纪要的"悬而未决"节中的问题，本次是否还在？
- 是 → 升级为 risk，建议创建专案级决策或升级沟通
- 已解决 → 在本次纪要中标注 ✓

**3.4 参会方画像积累**：

同一对方反复出现的关注点、偏好、禁忌，累积提示：
- "该客户连续 3 次会议关注交付时间 → 建议将交付节奏作为常规议题"
- "张工每次都会追问技术细节 → 下次准备详细方案"

**3.5 【MCP 通道】跨会话模式检测**：

Vault 的历史对照依赖已写入的会议纪要。MCP 可补充未写入 vault 的会话级经验：
- `memory_smart_search` 用参会人 + 风险关键词 → 找历史上与这些人的摩擦/障碍模式（即使没写成 insight）
- `memory_recall` 用项目名 + "承诺" "未兑现" → 找跨会话的承诺履约模式
- MCP 发现的模式与 vault 记录一致 → 提高置信度，标记 "vault + MCP 双重确认"
- MCP 发现但 vault 无记录 → 标记 "🆕 MCP 发现，建议确认后提取为 insight"

### Step 4: 创建会议纪要（主输出）

在 `Cards/reading/` 创建会议纪要笔记。

**设计约束：可被后续会议自动匹配。** 为此，纪要必须满足：
- 一致的 frontmatter 字段结构（`participants`、`project`、`meeting_date`、`meeting_type`、`prev_meeting`）
- 标准化的章节标题（"关键决议"、"行动项(我方)"、"行动项(对方/他人)"、"悬而未决"）
- 参会人命名一致（同一人每次用相同的名字）

```markdown
---
type: reading
subtype: meeting
domain: {推断}
status: processed
created: YYYY-MM-DD
meeting_date: YYYY-MM-DD
participants: [{我方}, {对方1}, {对方2}]
meeting_type: {客户会 | 内部协作 | 1-on-1 | 评审 | 培训 | 其他}
project: [[关联专案]]
source: [[Sources/processed/{filename}]]
related_tasks: [{涉及的任务 wikilink}]
related_decisions: [{产生的决策 wikilink}]
related_cards: [{交叉引用 wikilink}]
prev_meeting: [[上次会议纪要]] or null
---

# {会议主题} — {YYYY-MM-DD}

- ...
```

### Step 5: 统一确认界面（核心交互点）

向用户**一次性展示完整提议清单**，不分步确认：

```
═══ 会议处理报告 ═══
来源: {文件名}
推断: {会议身份摘要}

【知识卡片】
  1. 阅读摘要: Cards/reading/{文件名}
  2. atomic: "标题" — {一句话描述}
  3. insight: "标题" — {一句话描述}
  4. wikilink: {概念} → [[已有卡片]]

【决议】
  5. DEC-YYYY-NNN: {决议摘要}

【任务 — 新建】
  6. {A-F-O-T 标题} (截止: {日期})
  7. {A-F-O-T 标题} (⚠️ 截止日缺失，请补充)

【任务 — 更新】
  8. [[已有任务]]: {更新内容摘要}

【专案更新】
  9. [[专案名]]: {更新内容摘要}

【历史对照】(仅 deep 模式)
  ⚠️ 上次承诺"XXX"未跟进
  ⚠️ "YYY问题"连续2次未解决 → 建议升级

请确认: a 全部接受 / 输入编号选择 / edit 编辑某项 / skip 跳过
```

**确认规则**：
- `type/reading` — AI 自主创建（无需确认）
- `type/atomic`、`type/concept`、`type/insight` — 必须用户确认（铁律 1）
- `type/task` 新建 — 必须用户确认（权限矩阵）
- `type/task` 更新 — AI 自主（权限矩阵）
- `type/decision` — 必须用户确认（权限矩阵）
- Project 更新 — AI 自主（权限矩阵）

### Step 6: 执行与索引更新

用户确认后执行：

**6.1 创建/更新文件**（通过 Obsidian CLI）：

按确认结果依次创建/更新：
- 会议纪要 → `Cards/reading/`
- 原子/概念/洞察卡片 → `Cards/atomics/` 或 `Cards/concepts/` 或 `Cards/insights/`
- 决策记录 → `Decisions/DEC-YYYY-NNN.md`
- 新任务 → `Tasks/active/`
- 更新已有任务 → 追加进度日志
- 更新专案 → 追加问题/风险/任务清单

**6.2 源文件处理**：

- 将转录文件从 `Sources/inbox/` 移至 `Sources/processed/`

**6.3 索引更新**（AI 自主）：

- 更新 `index.md` 的对应分类
- 追加 `log.md`: `[YYYY-MM-DD HH:mm] meeting | {会议主题} | {mode} | {N} decisions, {M} tasks, {K} cards`
- 更新对应 domain 的 MOC
- 如果创建了 atomic 卡片，提醒用户："新卡片将在下次 /review 时进入复习队列"

## 模式差异

> fast/standard/deep 三种模式的能力矩阵见 [DETAIL.md](DETAIL.md)。核心差异：fast 只抓行动项+决议，standard 加知识提取+风险追踪，deep 加全量历史对照+MCP 跨会话检测。

## 特殊情况

- **转录极短**（< 3 个议题切换）：自动降级为 fast 模式，告知用户
- **纯状态同步会**（如站会，无决议无新行动项）：只创建纪要，跳过知识提取和任务创建，告知用户"本次无可提取行动项"
- **会议内容高度涉及某个活跃 Project**：优先以 Project 视角组织纪要，将 Project 名放入标题
- **同一参会人同日有多场会议**：询问用户是否合并处理还是分开
- **转录中明确提到已有 Task 的标题或编号**：自动匹配，不重新提议
- **用户选择 skip 跳过全部提议**：仍创建会议纪要（作为记录），但不创建任何衍生卡片/任务

## 🚫 不要做什么（反模式）

| # | 反模式 | 为什么不要做 | 正确做法 |
|---|--------|-------------|---------|
| 1 | **把会议纪要当逐字稿** | 逐字稿不可检索、不可复用，信息密度极低 | 按议题分块，标注 utterance 类型，提取关键点 |
| 2 | **所有"我觉得"都当成决议** | 个人观点不是决议——虚假决议污染决策链 | 决议必须是多方共识或决策者拍板的结论 |
| 3 | **把别人的承诺建成我的 Task** | 我只对自己的行动项负责 | 按说话人归属分流：我方→Task，他方→追踪列表 |
| 4 | **跳过 Step 0 直接处理** | 不确认会议身份和视角会导致行动项归属错误 | Step 0 必须确认：身份、视角、历史链接 |
| 5 | **deep 模式下跳过历史对照** | 承诺履约追踪和重复问题检测是会议飞轮的核心 | deep 模式必须执行 Step 3 全部对照 |
| 6 | **处理完后转录仍留在 inbox** | 未清理的源文件导致 inbox 膨胀 | Step 6 必须将源文件移至 processed/ |
| 7 | **跳过 MCP 只用 vault 做历史链接** | vault 只覆盖已写入的纪要——临时沟通和快速同步的历史不在其中 | Step 0.3 和 Step 3 必须双通道（vault + MCP），MCP 不可用时才降级为仅 vault |

## 失败处理

| 场景 | 处理 |
|------|------|
| **转录文件不存在或无内容** | 告知用户"文件路径无效或内容为空"，列出来源目录内容供选择 |
| **转录无说话人标记**（纯文本、无"某某:"格式） | 告知用户"转录缺少说话人标记，将以纯文本模式处理（无归属分流）" |
| **Step 0 推断失败**（会议类型/关联专案无匹配） | 标注"待确认"，不阻塞处理流程，在确认界面让用户补充 |
| **关联 Project 笔记不存在** | 跳过 Project 更新路径，标注"⚠️ 关联专案 [[X]] 不存在" |
| **Cards/reading/ 写入失败** | 直接在对话中展示纪要内容；告知用户"纪要未能写入文件，请检查 Obsidian 状态" |
| **所有提议被 skip** | 仍创建会议纪要（作为记录）并移动源文件；不创建任何衍生卡片/任务 |
| **AgentMemory MCP 不可用** | 跳过 MCP 通道，仅用 vault 搜索做历史链接和模式对照；在纪要中标注"ℹ️ MCP 不可用，历史上下文仅基于 vault" |

## 与其他技能的关系

> /meeting 通过 /decide、/task、/note、Project 更新四个通道分发产出。与 /ingest 的分工：/meeting 处理会议转录（承诺/决议/行动），/ingest 处理非会议材料（知识提取）。详细对比和关系图见 [DETAIL.md](DETAIL.md)。
