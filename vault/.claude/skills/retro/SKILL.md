# /retro Command

任务/项目复盘的**关键桥接技能**——将行动转化为知识。这是 ThinkFlywheel 飞轮的核心引擎。

## 核心理念

> "问题与吐槽"是知识原材料——每次摩擦都是经验数据。通过三向回流分发到正确位置:

```
任务完成
    ↓ /retro
    ├── 1. 通用方法论 → Cards/atomics/ + Cards/insights/ (原子卡片)
    ├── 2. 流程级经验 → Flows/{domain}/ (回写永久型任务笔记)
    └── 3. 专案级洞察 → Projects/active/ (更新专案经验区)
```

## Behavior

### Step 1: 确认复盘对象

- 如果用户指定了任务名: 直接定位
- 如果用户说"done"/"完成"/"做完了": 查找最近更新的 `status: done` 或 `status: doing` 任务
- 如果用户说"project retro": 定位项目笔记
- 如果有多个候选: 让用户选择

### Step 2: 读取原始材料

读取任务笔记中的：

1. **最终目标**: 最初设定的成功标准是什么？
2. **问题与吐槽**: 这是核心数据——每条都按日期记录了实际遇到的摩擦
3. **下一步行动**: 哪些完成了？哪些卡住了？哪些根本没开始？为什么？
4. **原始材料堆**: 哪些参考资料真正有用？哪些是噪音？

### Step 3: 模式分析

AI 分析"问题与吐槽"中的内容，寻找模式：

**问题分类**：
- **沟通问题**: "等反馈等了3天" → 模式: 依赖方响应慢
- **范围问题**: "需求又变了" → 模式: 项目范围不稳定
- **知识问题**: "不知道怎么用这个 API" → 模式: 技能缺口
- **流程问题**: "审批走了两遍" → 模式: 流程冗余
- **工具问题**: "XX 工具又崩了" → 模式: 工具不可靠
- **认知问题**: "一开始想复杂了" → 模式: 过度设计倾向

**跨任务模式检测（双通道：Vault + AgentMemory MCP）**：

1. **Vault 通道**：搜索 domain 相同的历史任务（Tasks/archived/），检查"问题与吐槽"中是否有相似的模式。
2. **【MCP 通道】AgentMemory 跨会话语义召回**：
   - `memory_smart_search` 用当前任务的关键词 + 问题类型搜索 → 找历史上类似讨论
   - `memory_recall` 用 domain + 摩擦类型召回 → 找以前遇到的类似障碍
   - MCP 可能发现**未写入 vault 的会话级经验**——这些是 vault 搜索无法覆盖的
3. **TM 过滤**：用 Hook 注入的 constraints 检查 MCP 召回的模式：
   - MCP 发现的模式是否与已知约束一致？
   - MCP 发现的模式是否与 profile 中的决策模式匹配？
4. **冲突处理**：
   - MCP 召回与 vault 记录冲突 → **vault 胜出**（ground truth）
   - MCP 发现 vault 中无记录的模式 → 标记为 "🆕 建议提取为新 insight"（待用户确认）
5. **综合判定**：如有跨任务重复的问题模式，标记为**"重复出现的模式"**——这是最有价值的 insight。标注来源（vault / MCP / 两者）。

### Step 4: 生成复盘摘要

在 `Reviews/retro/{Task Name} — Retro.md` 创建复盘笔记：

```markdown
---
type: review
domain: {domain}
status: final
created: YYYY-MM-DD
updated: YYYY-MM-DD
source: [[Tasks/active/{Task Name}]]
related_tasks: []
related_cards: []
---

# {Task Name} — 任务复盘

## 原始目标
{回顾最初设定的最终目标}

## 实际结果
{实际发生了什么}

## 差距分析
| 预期 | 实际 | 差距原因 |
|------|------|---------|
| ... | ... | ... |

## 关键教训
{从"问题与吐槽"中提炼的模式}

## 重复出现的模式 ⚠️
{如果有跨任务重复的问题模式}

## 提取的知识卡片
{/retro 自动提取的 insight + atomic 卡片列表}

## 下一步
**Start Doing**: {应该开始做的事}
**Stop Doing**: {应该停止做的事}
**Continue Doing**: {应该继续做的事}
```

### Step 5: 三向回流 — 知识提取与分发

复盘中的关键教训通过三条路径分发：

**路径 1: 通用方法论 → 原子卡片**

向用户展示提议:
```
📋 从这次任务中可以提取以下知识卡片：

🔗 已有卡片可关联:
- [[Card A]] — 这次任务验证了它的核心观点

🆕 建议新建卡片:
| # | 类型 | 标题 | 来源 |
|---|------|------|------|
| 1 | insight | "X类任务的范围管理陷阱" | 问题与吐槽 Day 3 |
| 2 | atomic | "Y工具的正确使用方式" | 问题与吐槽 Day 2 |

接受哪些？（全部/1,2/skip）
```

**路径 2: 流程级经验 → 回写 Flow**

如果任务 frontmatter 的 `flow` 字段非空:
1. 读取关联的 flow 笔记
2. 询问用户:"本次执行有什么对流程本身的改进建议?"
3. 如有改进:
   - 更新 flow 的"📋 标准步骤"或"⚠️ 易错点"
   - 递增 flow 的 `version` 字段
   - 追加 flow"📈 迭代日志": `[YYYY-MM-DD] v{n+1} | 来自 [[任务]] | 改动说明`
4. 如本次踩到新坑 → 追加到 flow"⚠️ 易错点"
5. 在任务"💡 复盘与衍生"中记录回写内容

**路径 3: 专案级洞察 → 更新 Project 经验区**

如果任务 frontmatter 的 `project` 字段非空:
1. 读取关联的 project 笔记
2. 检查任务"💡 复盘与衍生"是否有"专案级洞察"标记
3. 如有 → 追加到 project"💡 专案经验区"
4. 检查任务"💬 问题与吐槽" → 评估是否升级为专案级问题
5. 如有 → 追加到 project"🚧 专案级问题与决策"

### Step 6: 归档和更新（AI 自主）

1. 用户确认知识提取后:
   - 创建被接受的 insight + atomic 卡片
   - 新 atomic 卡片自动注册到 FSRS
   - 新卡片 frontmatter 中 `source` 回链到复盘笔记
2. 任务笔记: `status` 改为 `archived`，移至 `Tasks/archived/`
3. 更新关联专案:
   - 任务清单对应行从 🔲 改为 ✅,追加完成日期
   - 重新触发 project 进度评估
   - 将专案级洞察追加到 project"💡 专案经验区"
4. 更新关联流程:
   - 如有改进,更新 flow 步骤/易错点,递增 version,追加迭代日志
5. 更新索引:
   - `index.md`: 从 "Active Tasks" 移除
   - `log.md`: `## [YYYY-MM-DD] retro | {Task Name} | {n} insights | flow: {flow} | project: {project}`
6. 向用户报告: "{Task Name} 已完成归档。提取 {n} 张卡片,回写 {f} 条流程经验,更新 {p} 条专案洞察。"

## 🚫 不要做什么（反模式）

| # | 反模式 | 为什么不要做 | 正确做法 |
|---|--------|-------------|---------|
| 1 | **跳过 Step 1 直接复盘** | 复盘对象不明确会导致分析偏差 | 必须先确认复盘对象（任务名/最近 done 任务/项目） |
| 2 | **把"问题与吐槽"当抱怨垃圾桶** | 每条吐槽都是知识原材料，忽略=浪费经验 | 逐条分析、分类、寻找跨任务模式 |
| 3 | **复盘时只提取负面教训** | 成功经验同样有价值——可复制的模式比避坑清单更有用 | 任务没有吐槽时主动提取成功模式 |
| 4 | **跳过三向回流直接把 insight 写入卡片** | 违反铁律 1——知识写入必须双提议 | Step 5 必须展示提议列表，用户确认后写入 |
| 5 | **复盘后不归档直接留在 active/** | 任务不归档会导致索引混乱、活跃任务列表膨胀 | Step 6 必须改 status→archived、移文件、更新索引 |
| 6 | **MCP 召回的模式直接当事实写入 insight** | MCP 是中精准语义召回，可能混淆不同会话的上下文 | MCP 发现的模式必须用 vault 内容验证，无 vault 记录 → 标记为"建议提取"，待用户确认 |
| 7 | **只用 vault 搜索不用 MCP（对历史查询型复盘）** | 部分经验只在会话中讨论过，从未写入 vault | 跨任务模式检测必须双通道（vault + MCP），MCP 不可用时才降级为仅 vault |

## 失败处理

| 场景 | 处理 |
|------|------|
| **找不到 done 状态的任务** | 列出最近更新的任务（不限状态），让用户选择复盘对象 |
| **任务没有"问题与吐槽"内容** | 走"成功模式提取"路径——分析为什么顺利，提取可复制经验 |
| **三向回流时 flow/project 字段为空** | 跳过对应回流路径，不强制；告知用户"如该任务属于某流程/专案，可先设置关联再复盘" |
| **关联的 flow 或 project 笔记不存在** | 跳过该回流路径，标注"⚠️ 关联笔记 [[X]] 不存在，回流跳过" |
| **Reviews/retro/ 目录不存在** | 创建目录；失败则直接写入 Reviews/ 根目录，告知用户 |
| **FSRS 注册失败**（新 atomic 卡片） | 不阻塞复盘流程；在日志中记录"⚠️ N 张卡片未注册到 FSRS"，下次 /review 时自动补注册 |
| **AgentMemory MCP 不可用** | 跳过 MCP 通道，仅用 vault 搜索做跨任务模式检测；在复盘摘要中标注"ℹ️ MCP 不可用，跨会话模式检测仅基于 vault" |

---

## 特殊情况

- **任务没有"问题与吐槽"**: 复盘更有价值——"为什么这次这么顺利？" 提取可复制的成功模式
- **任务中途放弃**: 复盘更有价值——"放弃是对的决策还是逃避？" 提取决策判断标准
- **任务关联了活跃项目**: 检查是否影响项目里程碑
- **同一个项目中多个任务暴露出相同模式**: 升级为项目级风险
