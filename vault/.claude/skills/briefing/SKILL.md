# /briefing Command

生成每日上下文简报。这是 ThinkFlywheel 的**核心融合点**——任务层(L3)、知识层(L2)、记忆层(L1)在此交汇为一张可操作的早晨视图。

## 核心理念

不是让你从空白开始每一天。而是把系统里所有与你相关的上下文——你在做什么、你知道什么、你该复习什么、哪些项目需要关注——全部汇总到一个地方。

## Behavior

### Step 0: 处理上轮会话待审（Stop Hook 遗留）

检查 Stop Hook 在上轮会话结束时留下的待处理标记。

> **铁律：Step 0 必须调用 MCP 工具。** 单次 transcript 文件只覆盖最近一次会话，MCP 覆盖全部历史。跳过 MCP = 丢失跨会话模式检测。看到 transcript 路径就跳过 MCP 是本步骤最常见的错误。

1. 读取 `.claude/memory/.stop-state.json`
2. 如果 `pending_review: true` 且 `last_session_file` 非空：
   a. 读取 `last_session_file` 指向的会话骨架文件
   b. **【强制】调用 AgentMemory MCP 召回上轮会话**（两步都必须执行）：
      - `memory_sessions` → 列出最近 5 个 session，了解近期会话密度和模式
      - `memory_smart_search` 查询上轮会话的主题关键词（从骨架文件的 `session_id` 或用户查询中提取）→ 跨所有历史 session 召回相关内容
   c. **【可选补充】读取 transcript 文件**（骨架 frontmatter 中的 `transcript` 路径）——仅当 MCP 召回结果不足以还原会话细节时。优先信任 MCP 的跨会话视角。
   d. **填写会话摘要**：综合 MCP 召回 + transcript（如有），填写：
      - 关键决策（如有）
      - 新建/修改的文件列表
      - Agent 被纠正的情况（如有）
      - 新用户 assertion（如有）
   e. **检测新 assertion → 对比 profile.yaml**：
      - 如果用户在会话中表达了新的偏好/优先级/决策模式 → 与 profile.yaml 现有条目对比
      - 如有冲突 → 在简报中提醒用户确认："⚠️ 检测到可能与 profile 冲突的新信息：[具体内容]。需要更新 profile.yaml 吗？"
      - 如无冲突但值得记录 → 提议添加并展示建议条目
   f. **检测 Agent 被纠正 → 写 agent-log**：
      - 如果用户在本会话中纠正了 Agent 的错误 → 按 agent-log 格式追加教训条目
      - 格式：`- **错误**: {具体错误} → **原因**: {根因} → **教训**: {避免方法} → **tags**: #{标签}`
   g. **检测新约束声明 → 提醒确认**：
      - 如果用户表达了新的硬性约束或边界 → 提醒："⚠️ 检测到可能的新约束：[具体内容]。需要加入 constraints.yaml 吗？"
   h. **同步到 AgentMemory MCP**：将确认的事实调用 `memory_save` 存入 MCP
   i. 将会话骨架的 `status` 改为 `reviewed`，更新 `ended` 为实际完成时间
   j. 设置 `.stop-state.json` 的 `pending_review: false`
3. 如果 `pending_review: false` 或文件不存在 → 跳过，正常执行后续步骤

> **注意：** Step 0 不自动修改 profile.yaml 或 constraints.yaml——只提议，等待用户确认。agent-log.md 的写入需基于明确可识别的纠正事件，不臆造。

### Step 1: 扫描活跃任务

读取 `Tasks/active/` 下所有任务笔记，提取：

- 任务标题 + wikilink
- `status`: 特别标记 `waiting` 状态的任务（阻塞中）
- `domain`
- 最新"下一步行动"中未勾选的条目
- `updated` 日期：标记超过 7 天未更新的任务 ⚠️，超过 14 天的 🔴
- `due` 日期：标记 3 天内到期的 🔴，7 天内 ⚠️

按优先级排序：
1. 即将到期的任务
2. doing 状态 > waiting 状态 > todo 状态
3. 最近更新过的在前

### Step 2: 检测到期复习卡片

调用 FSRS-6 引擎获取今日到期卡片：

```bash
python .obsidian/scripts/fsrs_engine.py .obsidian/review_state.json due --limit 20
```

对每张到期卡片：
- 读取卡片内容，提取主题关键词
- 按 `domain` 分组

### Step 2b: 检测今日触发的永久型流程 🆕

扫描 `Flows/` 下所有 `type: flow` 且 `status: active` 的笔记,检查 `trigger` 字段:

- `weekly-fri` → 今天是否周五? → 提示"今天该执行 [[周报撰写流程]] 了,是否创建本周任务?"
- `weekly-mon` → 今天是否周一?
- `monthly-1` → 今天是否本月1日?
- `on-demand` → 不主动提示
- `event:xxx` → 预留

对每个今日触发的流程:
- 列出流程名称和最近一次执行记录
- 询问用户是否激活(自动创建 /task,flow 字段预填,步骤继承自流程)
- 用户同意 → 调用 `/task` 创建逻辑

### Step 3: 交叉引用（核心融合）

对每张到期复习卡片，搜索 vault 中是否存在关联：

1. 卡片 frontmatter 中是否有 `related_tasks`？如果有，直接建立链接
2. 卡片的 `domain` 与哪些活跃任务的 `domain` 匹配？
3. 卡片标题/内容中的关键词是否出现在活跃任务的"原始材料堆"中？

结果：每张复习卡片标记为：
- **"关联活跃任务"** — 标注重点复习 + 标注关联任务名
- **"无关联任务"** — 你的知识库中有这块知识，但当前没有在用的任务

### Step 4: 检查项目健康

读取 `Projects/active/` 下所有项目，提取进度脉搏：

- on-track: 绿色 🟢
- at-risk (有阻塞任务或里程碑逾期): 黄色 ⚠️
- stalled (14 天以上无任务活动): 红色 🔴

### Step 5: 历史预警

扫描 `Tasks/archived/` 中与当前活跃任务 domain 相同的历史任务，检查：

- 历史任务的"问题与吐槽"中是否有重复出现的模式？
- 当前活跃任务是否有类似的特征（相似的最终目标、相似的材料堆）？
- 如果有，提取为"历史警告"

### Step 6: 生成简报

按以下结构输出 `Daily/YYYY-MM-DD.md`（如果今天已有则直接展示）：

```markdown
# {{date}} 每日简报

## 🔥 今日焦点（1-3 个最重要的事）
{从活跃任务中选出最紧急/重要的 1-3 项}

## 📋 活跃任务
| 优先级 | 任务 | 状态 | 下一步 | 更新 |
|--------|------|------|--------|------|
| HIGH | [[Task A]] | doing | review draft | 今天 |
| MEDIUM | [[Task B]] | waiting | 等反馈 | 3天前 ⚠️ |

## 🧠 今日复习（FSRS 到期卡片）
| 卡片 | 关联任务 | 
|------|---------|
| [[SBI 反馈框架]] | → [[Task B]] 💡 |
| [[数据可视化的3原则]] | (无关联任务) |

## 📊 项目健康
| 项目 | 状态 | 活跃任务数 | 本周完成 |
|------|------|-----------|---------|
| [[Project X]] | 🟢 on-track | 3/5 | 2 |
| [[Project Y]] | 🔴 stalled | 0 | 0 |

## 🔄 今日流程触发
{如果有今日触发的永久型流程}
| 流程 | 触发条件 | 上次执行 | 操作 |
|------|---------|---------|------|
| [[周报撰写流程]] | 每周五 | 7天前 | 是否创建本周任务? |

## ⚠️ 历史预警
{从历史类似任务的"问题与吐槽"中发现的可能模式}

## 📝 今日概览
- 活跃任务: {count}
- 到期复习: {count}
- 阻塞任务: {count}
- 即将到期: {count}
- 今日触发流程: {count}
```

### Step 7: 更新索引

- 更新 `log.md`: `## [YYYY-MM-DD] briefing | daily context generated`
- Daily 文件保留最近 14 天，AI 检查并提示清理旧的

## 失败处理

| 场景 | 处理 |
|------|------|
| **FSRS 引擎不可用**（fsrs_engine.py 未找到或 Python 不可用） | 跳过"今日复习"和"历史预警"节，在简报顶部标注："⚠️ FSRS 引擎不可用，今日复习数据缺失" |
| **Tasks/active/ 为空** | "今日焦点"节显示"当前无活跃任务"，其余节正常生成 |
| **Projects/active/ 为空** | "项目健康"节显示"当前无活跃专案" |
| **Flows/ 目录为空或无匹配 trigger** | 跳过"今日流程触发"节 |
| **Daily/ 文件写入失败** | 直接在对话中展示简报内容，告知用户"简报未能写入文件，但内容已生成于上方" |
| **review_state.json 损坏或为空** | 跳过复习节，标注"⚠️ review_state.json 不可用，请运行 /review 初始化" |

## 🚫 不要做什么（反模式）

| # | 反模式 | 为什么不要做 | 正确做法 |
|---|--------|-------------|---------|
| 1 | **在简报中直接创建/修改任务** | 简报是只读视图，写入操作属于 /task 和 /retro | 只展示状态和建议，不直接编辑 |
| 2 | **简报为空时报错或跳过** | vault 初期无内容是正常状态 | 用"当前无活跃任务/专案/卡片"明确告知，不静默跳过 |
| 3 | **对触发流程自动创建任务** | 违反铁律——task 创建需要用户确认 | 询问用户是否激活，同意后才创建 |
| 4 | **交叉引用时编造关联** | 虚假关联污染知识图谱 | 只基于 frontmatter 的 related_tasks/related_cards 和 domain 匹配建立关联 |
| 5 | **将简报当作任务执行工具** | 简报是"视图"不是"工具"——它展示状态，不执行动作 | 需要执行操作时引导用户使用对应技能（/task、/retro、/review） |
| 6 | **简报内容超过一屏（~50行）** | 信息过载违背简报的"单页视图"设计目标 | 精简到核心：焦点→任务→复习→专案→预警，详情通过 wikilink 跳转 |

---

## 注意事项

- 简报是**临时性文件**，每天重新生成，不累积
- 交叉引用是简报的核心价值——不是简单的列表，而是**有上下文的关联**
- 如果 vault 中还没有内容（Phase 1 初期），简报只显示活跃任务部分——这很正常
- "历史预警"在 Phase 1-2 数据不足时可能为空——随着使用积累会逐渐有价值
- 简报以只读展示为主，Step 2b 的流程激活询问是**唯一交互点**——仅在检测到今日触发流程时出现
